## 2. 레이어 구조 (Backend)

```
Router      →  요청/응답 처리, 라우팅, Dependency(인증/인가) 적용
   ↓
Service     →  비즈니스 로직 (파싱·청킹, RAG 검색·답변 생성, 세션 관리 등)
   ↓
Repository  →  SQLAlchemy를 통한 DB 접근 (문서/청크/세션 모델 기반)
   ↓
PostgreSQL + pgvector  →  데이터·벡터 저장
```

각 도메인(Auth, Documents, Chat, Admin)은 FastAPI 라우터 모듈 단위로 분리되어 있으며, 모듈 간 의존성은 최소화하여 독립적으로 개발/테스트 가능하도록 구성한다.

## 4. 인증/인가 흐름

```
1. 회원가입: POST /auth/signup → bcrypt 해시 저장
2. 로그인:   POST /auth/login  → JWT 발급 (payload: {sub: userId, role})
3. 이후 요청: Authorization: Bearer <token> 헤더 첨부
4. 서버:     JWTAuthDependency가 토큰 검증 → 리소스 소유자(owner_id) 검사 → 통과 시 라우터 진입
```

- `JWTAuthDependency`: 토큰 유효성만 검증 (로그인 여부)
- 소유자 검증: `document.owner_id == current_user.id` 등, 역할(role)보다 "본인 리소스인지"가 핵심 검사 대상

## 5. 핵심 도메인 흐름 (문서 질의응답 프로세스, Phase 1)

```
[사용자] 문서 업로드 (status: PARSING)
      │
      ▼
[시스템] 파싱·청킹·임베딩 (status: READY)
      │
      ▼
[사용자] 질문 입력 → 벡터 검색(pgvector) → LLM 답변 생성 (인용 포함)
      │
      ▼
[사용자] 인용 클릭 → 원본 PDF 해당 페이지로 이동·하이라이팅
      │
      ▼
[관리자] 전체 문서/세션/토큰 사용량 모니터링
```

## 6. 데이터 흐름 예시 — "사용자가 질문을 입력해서 답변 받기"

```
1. Frontend: POST /chat/sessions/3/query  (Authorization 헤더에 JWT 포함, body: question)
2. Backend Router: JWTAuthDependency → 세션 소유자(owner_id) 검증 통과
3. ChatService.query(sessionId=3, question=...)
     → pgvector로 관련 청크 검색 (cosine similarity Top-K)
     → LLMProvider.generate(prompt) 호출 (API 또는 로컬, .env 설정에 따라 분기)
4. Repository: ChatMessage 테이블에 INSERT (question/answer), Citation 테이블에 근거 청크 매핑
5. Response: StreamingResponse로 토큰 단위 SSE 전송
6. Frontend: EventSource로 수신하며 실시간 렌더링, 인용 뱃지 표시
```

## 7. 배포 아키텍처

```
GitHub Repository
   ├── backend/  → Railway/Render 또는 AWS EC2 (FastAPI 앱 + 환경변수: DB_HOST, JWT_SECRET, LLM_PROVIDER 등)
   │                    ↓
   │              PostgreSQL + pgvector (Railway/AWS RDS 등 매니지드 DB)
   │
   └── frontend/ → Vercel (Next.js 자동 빌드/배포)
                        ↓
                 NEXT_PUBLIC_API_URL 환경변수로 백엔드 주소 연결
```

- CORS는 백엔드에서 프론트엔드 배포 도메인만 허용하도록 배포 전 제한 필요
- LLM API 키는 백엔드 환경변수로만 보관, 프론트엔드에 절대 노출하지 않음

## 8. 향후 확장 아키텍처 (Phase 2~3, 기획 단계 — 이번 구현 범위 아님)

### 8.1 Phase 2 — 검색 정밀도 고도화 흐름

```
[문서 업로드/파싱 시]
  Chunk.text
        │
        ▼
  BM25 인덱싱 (키워드 검색용) + pgvector 임베딩 (의미 검색용)
        │
        ▼
  Ensemble Retriever (하이브리드 검색 결과 병합)

[질의 시]
  Top-20 1차 검색 결과
        │
        ▼
  PyTorch Cross-Encoder Re-ranker (`klue/roberta-base` 파인튜닝)   ← 우리 서버가 직접 서빙 (외부 API 아님)
        │
        ▼
  Top-3 정밀 문맥 → LLM Provider로 답변 생성
```

- Re-ranker는 자체 파인튜닝 모델로 서빙되며, 1차 검색(BM25+pgvector)만 통과한 후보를 재정렬하는 역할
- PII 마스킹은 임베딩 이전 단계에서 적용해 민감정보가 벡터에도 남지 않도록 처리

### 8.2 Phase 3 — 성능/안정성 확장

```
              ┌─────────────┐
   Client ──▶ │  Backend    │
              └──────┬──────┘
                     │
           ┌─────────┴─────────────────┐
           ▼                           ▼
     ┌──────────────┐           ┌─────────────────────┐
     │ Celery+Redis  │           │ PostgreSQL+pgvector  │
     │ (비동기 큐)    │           │  (원본 데이터·벡터)     │
     └──────────────┘           └─────────────────────┘
           │
           ▼
     ┌──────────────┐
     │ LangSmith     │
     │ (MLOps 트레이싱) │
     └──────────────┘
```

- **비동기 처리**: 대용량 문서 파싱·임베딩을 Celery 워커로 분리해 API 서버 블로킹 방지
- **관측성**: LangSmith/Phoenix로 토큰 사용량·지연 시간·검색 품질(Ragas) 추적
- **동시성 제어**: 동일 문서 재파싱 요청 시 Redis Lock으로 중복 처리 방지

이 확장 영역은 Phase 1 완료 후 별도 스프린트로 진행하며, 이번 아키텍처(1~7번)에는 영향을 주지 않습니다.
