## 1. 프로젝트 개요

**서비스명**: 멀티모달 문서 분석 & 대화형 지식베이스 플랫폼 (DocuMind AI)

**한 줄 소개**: 사용자가 업로드한 문서를 AI가 파싱·임베딩해두고, 질문하면 문서 근거(출처 페이지)와 함께 답하는 RAG 기반 대화형 지식베이스 서비스

| 항목 | 내용 |
| --- | --- |
| 팀 구성 | 2인 (기능별 풀스택 담당) + Claude Code(AI 페어 프로그래밍 도구) |
| 개발 방식 | Claude Code CLI를 활용한 보일러플레이트/테스트 코드 생성으로 개발 속도 확보 |
| 목적 | RAG 기반 AI 서비스를 A-Z 풀스택으로 구현한 AI Full-Stack Engineer 포지션 지원용 포트폴리오 확보 |

## 2. "RAG 파이프라인"이란

사용자가 올린 문서를 AI가 "먼저 찾아 읽고, 그다음 답한다"는 구조입니다. 일반 LLM이 아는 척 답하는 것과 달리, 실제 문서 내용을 근거로 답하고 출처(페이지)까지 제시합니다.

| RAG 도메인 | 일반 검색엔진 비유 |
| --- | --- |
| 문서(Document) | 색인 대상 웹페이지 |
| 청크(Chunk) | 페이지를 문단 단위로 쪼갠 색인 항목 |
| 임베딩(Embedding) | 검색어와 문단의 "의미"를 좌표로 변환한 값 |
| 검색(Retrieval) | 질문과 가장 가까운 좌표의 문단 찾기 |
| 인용(Citation) | 검색 결과에 달리는 "출처 링크" |

문서 업로드 시 처리 항목: 파일명, 소유자, 파싱 상태(status), 페이지 수, 청크 개수, 업로드 일시.

## 3. 사용자 유형 정의

> 그룹웨어의 "결재 권한"만큼 복잡하진 않지만, RAG 서비스도 **본인 문서·세션만 접근 가능**이라는 원칙이 핵심입니다.
> 

| 유형 | 정의 | 특징 |
| --- | --- | --- |
| **비로그인** | 로그인하지 않은 상태 | 메인 화면(서비스 소개)·로그인·가입 요청 외 접근 불가 |
| **일반 사용자(USER)** | 소속 회사 관리자가 발급한 계정으로 로그인한 사용자 | 본인 문서 업로드/조회/삭제, 본인 채팅 세션 생성/조회, RAG 질의응답 |
| **회사 관리자(ADMIN)** | 마스터 계정의 승인을 거쳐 발급된 회사(기업) 단위 관리자 | USER 권한 + **자사(같은 회사) 소속** 문서/세션/토큰 사용량 리스트 조회(Admin 대시보드), 소속 사용자 계정 발급 |
| **마스터(MASTER)** | 서비스 운영사(플랫폼)의 최상위 계정 | 회사 가입 요청 검토·승인/반려, 승인 시 회사 ADMIN 계정 발급, 전체 회사 현황 관리 |

> **핵심 원칙**: 문서함은 **개인 문서함**(`owner_id` 기준, 본인만 접근)과 **회사 문서함**(`companyId` 기준, 같은 회사 소속이면 누구나 조회·질의 가능)으로 나뉜다. 채팅 세션도 마찬가지로 `owner_id` 기준 본인 것만 접근 가능. ADMIN은 **같은 `companyId`** 소속 리소스의 현황만 조회할 수 있고(개인 문서함 내용 자체에는 접근하지 않음), MASTER는 회사 단위 가입 요청과 계정 발급을 관리할 뿐 개별 문서·대화 내용에는 접근하지 않는다. 역할(role) 체계는 USER/ADMIN/MASTER 3단계로 단순화해 인증 로직에 시간을 쏟지 않고 RAG 파이프라인 구현에 집중한다.
>

## 4. 기능 목록 (모듈별)

> 우선순위 — **필수**: 없으면 서비스가 동작하지 않는 핵심 / **추가**: Phase 2~3 확장 계획(기획만)
> 

### 4.1 인증 / 계정 발급

| 기능 | 접근 권한 | 우선순위 | 설명 |
| --- | --- | --- | --- |
| 가입 요청(회사 단위) | 비로그인 | 필수 | 회사대표가 회사이름·사업자번호·전화번호·이메일·회사규모(인원수)를 입력해 마스터 계정에 요청. 인원수 기준 제한 토큰양이 자동 계산되어 함께 제출됨 | 추후개선 : 사용해보고 토큰양 계산해서 책정 |
| 가입 요청 검토/승인·반려 | MASTER | 필수 | 요청 검토 후 승인 시 해당 회사 ADMIN 계정 생성 + 회사 전체 토큰 한도(`Company.tokenLimit`) 책정(자동계산값을 기본 제안, 마스터가 조정 가능), 등록된 전화번호·이메일로 별도 연락해 계정 정보 안내(반려 시 사유 통지) |
| 소속 사용자 계정 발급 | ADMIN | 필수 | 발급받은 회사 계정으로 로그인 후, 소속 직원(USER) 계정을 생성·초대 |
| 로그인 | 비로그인 | 필수 | 이메일·비밀번호 입력, JWT(Access Token) 발급 (USER/ADMIN/MASTER 공통) |
| 로그아웃 | USER 이상 | 필수 | 클라이언트 토큰 폐기 |
| 마이페이지 조회/수정 | 본인 | 필수 | 계정 정보 확인·수정 |

> 개인이 임의로 회원가입할 수 없는 구조입니다. **회사 단위 가입 요청 → 마스터 승인 → ADMIN 계정 발급 → ADMIN이 사내 USER 계정 발급**의 3단계 온보딩으로 진행됩니다.
> 

### 4.2 문서 관리 (A 담당)

| 기능 | 접근 권한 | 우선순위 | 설명 |
| --- | --- | --- | --- |
| 개인 문서함 업로드 | 본인 | 필수 | PDF 업로드 → 파싱 상태 `PARSING`으로 생성. 본인만 조회 가능 |
| 회사 문서함 업로드 | USER 이상(같은 회사) | 필수 | 승인 절차 없이 즉시 업로드. 파일 콘텐츠 해시(SHA-256)를 계산해 같은 회사 문서함 내 완전 동일 파일이 있으면 업로드를 차단하고 기존 문서로 안내(중복 방지) |
| 파싱·청킹·임베딩 | 시스템(LangChain) | 필수 | 개인/회사 문서함 공통. 텍스트·표 추출 → 청크 분할 → 임베딩 후 pgvector 저장, 완료 시 `READY`(실패 시 `FAILED`) |
| 문서 목록/상세 조회 | 개인 문서함: 본인 / 회사 문서함: 같은 회사 소속 전원 | 필수 | 파일명·페이지 수·청크 수·파싱 상태 표시 |
| 문서 삭제 | 개인 문서함: 본인 / 회사 문서함: 업로더 본인 또는 ADMIN | 필수 | 문서 및 연관 청크 삭제 |

### 4.3 RAG 질의응답 + 세션 관리 (B 담당)

| 기능 | 접근 권한 | 우선순위 | 설명 |
| --- | --- | --- | --- |
| 채팅 세션 생성/목록/히스토리 | 본인 | 필수 | 세션 생성 시 검색 스코프(**개인 문서함** / **회사 문서함**)를 먼저 선택. 대화 세션 단위로 히스토리 저장·복원 |
| RAG 질의응답 | 본인 | 필수 | 질문 → 세션에 지정된 스코프 내에서 벡터 검색 → LLM 답변 생성(근거 페이지 인용) → SSE 스트리밍 |
| 인용 하이라이팅 | 본인 | 필수 | 답변의 인용 클릭 시 PDF 뷰어에서 해당 페이지·구간 하이라이트 |
| 하이브리드 검색(BM25+Dense) | 본인 | 추가(Phase 2, 기획만) | 검색 정밀도 고도화 |
| Cross-Encoder Re-ranker | 본인 | 추가(Phase 2, 기획만) | PyTorch 파인튜닝 기반 재정렬 |
| PII 마스킹 / 프롬프트 인젝션 방어 | 시스템 | 추가(Phase 2, 기획만) | 보안 강화 |

### 4.4 회사 관리자 (Admin, B 담당)

| 기능 | 접근 권한 | 우선순위 | 설명 |
| --- | --- | --- | --- |
| 자사 문서 리스트 조회 | ADMIN | 필수 | 같은 회사(companyId) 소속 사용자 문서 현황 |
| 자사 세션 리스트 조회 | ADMIN | 필수 | 같은 회사 소속 사용자 채팅 세션 현황 |
| 자사 토큰 사용량 조회 | ADMIN | 필수 | 회사에 배정된 제한 토큰양 대비 사용량 집계(LLM API 호출 토큰 기준) |
| 소속 사용자 계정 관리 | ADMIN | 필수 | 사내 USER 계정 생성/초대/비활성화 |
| 소속 사용자 토큰 한도 배분 | ADMIN | 필수 | 마스터가 책정한 회사 전체 한도(`Company.tokenLimit`) 내에서 인당 토큰 한도(`User.tokenLimit`)를 배분·조정. 배분 합계는 회사 전체 한도를 초과할 수 없음 |

### 4.5 마스터 (Master, B 담당)

| 기능 | 접근 권한 | 우선순위 | 설명 |
| --- | --- | --- | --- |
| 가입 요청 리스트 조회 | MASTER | 필수 | 대기중/승인/반려 상태별 회사 가입 요청 현황 |
| 가입 요청 승인/반려 | MASTER | 필수 | 승인 시 회사 ADMIN 계정 자동 생성 + 연락처로 안내, 반려 시 사유 기록 |
| 회사 토큰 한도 책정/조정 | MASTER | 필수 | 회사 전체 토큰 한도(`Company.tokenLimit`) 책정(승인 시 자동계산값을 기본 제안, 이후에도 언제든 조정 가능) |
| 전체 회사 리스트 조회 | MASTER | 필수 | 승인된 회사별 인원수·제한 토큰양·현재 사용량 현황 |

## 6. 화면 및 URL 설계

### 6.1 사이트맵

```
/                                        [공통] 메인화면 (비로그인 접근 가능)
│   ├─ 서비스 소개 / 히어로 섹션
│   ├─ "문서를 업로드하고 AI에게 물어보세요" 데모 미리보기
│   └─ "무료로 시작하기" CTA → /request 연결 (회사 가입 요청)
│
/login                                   [공통]
/request                                 [공통] 회사이름·사업자번호·전화번호·이메일·인원수 입력 → 마스터 계정에 가입 요청
│
├─ (USER/ADMIN 로그인 시)
│   ├─ /documents                       [A] 개인 문서함 목록, 업로드
│   ├─ /documents/[id]                  [A] 개인 문서 상세(파싱 상태·메타정보)
│   ├─ /documents/company               [A] 회사 문서함 목록, 업로드(승인 없음, 중복 파일 자동 차단)
│   ├─ /documents/company/[id]          [A] 회사 문서 상세
│   ├─ /chat                            [B] 세션 목록, 새 세션 시작 시 스코프(개인/회사 문서함) 선택
│   ├─ /chat/[sessionId]                [B] Split-View 채팅 + PDF 뷰어
│   └─ /mypage                          [공통] 계정 정보
│
├─ (ADMIN 로그인 시, 추가)
│   ├─ /admin                           [B] 자사 문서/세션/토큰 사용량 리스트
│   └─ /admin/members                   [B] 소속 사용자(USER) 계정 관리
│
└─ (MASTER 로그인 시)
    ├─ /master/requests                 [B] 가입 요청 리스트·승인/반려
    └─ /master/companies                [B] 전체 회사 현황(인원수·토큰 한도·사용량)
```

### 6.2 화면별 상세

| 화면 | 경로 | 담당 | 주요 구성 요소 |
| --- | --- | --- | --- |
| 메인화면 | `/` | 공통 | 서비스 소개, 데모 미리보기, "무료로 시작하기" CTA |
| 로그인 | `/login` | 공통 | 이메일/비밀번호 입력, 로그인 버튼 |
| 가입 요청 | `/request` | 공통 | 회사이름·사업자번호·전화번호·이메일·회사규모(인원수) 입력, 제한 토큰양 자동 계산 표시 후 제출 |
| 개인 문서함 | `/documents` | A | 카드형 목록, 파싱 상태 뱃지, 업로드 버튼(본인만 조회) |
| 개인 문서 상세 | `/documents/[id]` | A | 파일명/페이지수/청크수, 삭제 버튼 |
| 회사 문서함 | `/documents/company` | A | 카드형 목록(같은 회사 소속 전원 조회), 업로드 버튼(승인 없음, 중복 파일 업로드 시 안내) |
| 회사 문서 상세 | `/documents/company/[id]` | A | 파일명/업로더/페이지수/청크수, 삭제 버튼(업로더 본인·ADMIN만) |
| 세션 목록 | `/chat` | B | 과거 대화 세션 목록, 새 세션 시작 시 검색 스코프(개인 문서함/회사 문서함) 선택 |
| 채팅 화면 | `/chat/[sessionId]` | B | 좌: 대화창(SSE 스트리밍), 우: PDF 뷰어(인용 하이라이팅, 회사 문서함 스코프는 인용마다 문서 전환 가능해야 함) |
| 마이페이지 | `/mypage` | 공통 | 계정 정보 확인·수정 |
| Admin 대시보드 | `/admin` | B | 자사 문서/세션/토큰 사용량 테이블, 검색·필터 |
| 소속 사용자 관리 | `/admin/members` | B | 사내 USER 계정 목록, 생성/초대/비활성화, 회사 전체 한도 내 인당 토큰 한도 배분(잔여 배분 가능량 표시) |
| 가입 요청 관리 | `/master/requests` | B | 대기/승인/반려 상태별 요청 리스트, 승인 시 ADMIN 계정 자동 생성 + 회사 토큰 한도 책정(자동계산값 기본 제안, 수정 가능) |
| 회사 현황 | `/master/companies` | B | 승인된 회사별 인원수·제한 토큰양(조정 가능)·사용량 현황 |

### 6.3 API 설계 (FastAPI 라우터 기준)

```
[인증 / 계정]
POST  /signup-requests         회사 가입 요청 생성(회사이름·사업자번호·전화번호·이메일·인원수) ← 비로그인
POST  /auth/login              로그인 (JWT Access Token 발급)                        ← 비로그인
GET   /users/me                내 정보 조회                                          ← 로그인
PATCH /users/me                내 정보 수정                                          ← 로그인

[문서 관리] (A 담당)
GET    /documents                내 개인 문서함 목록 조회       ← 로그인
POST   /documents                개인 문서함 업로드(파싱·청킹·임베딩 파이프라인 트리거) ← 로그인
GET    /documents/{id}           개인 문서 상세 조회             ← 소유자
DELETE /documents/{id}           개인 문서 삭제(연관 청크 포함)  ← 소유자

GET    /company-documents        회사 문서함 목록 조회           ← 로그인(같은 회사)
POST   /company-documents        회사 문서함 업로드 — 콘텐츠 해시(SHA-256)로 같은 회사 내 완전 동일 파일 여부 검사 후 중복이면 409 반환, 승인 절차 없음 ← 로그인(같은 회사)
GET    /company-documents/{id}   회사 문서 상세 조회             ← 같은 회사
DELETE /company-documents/{id}   회사 문서 삭제                  ← 업로더 본인 또는 ADMIN

[채팅 / RAG 질의응답] (B 담당)
GET  /chat/sessions                  내 세션 목록 조회         ← 로그인
POST /chat/sessions                  세션 생성(body에 scope: PERSONAL|COMPANY 지정) ← 로그인
GET  /chat/sessions/{id}/messages    세션 히스토리 조회        ← 소유자
POST /chat/sessions/{id}/messages    질문 전송 → 세션의 scope 내에서 벡터 검색 → LLM 답변(SSE 스트리밍, 인용 포함) ← 소유자

[회사 관리자] (B 담당)
GET   /admin/documents          자사 문서 리스트                 ← ADMIN
GET   /admin/sessions           자사 세션 리스트                 ← ADMIN
GET   /admin/usage              자사 토큰 사용량 집계             ← ADMIN
GET   /admin/members            소속 사용자 목록(개인별 tokenLimit·tokenUsed 포함) ← ADMIN
POST  /admin/members            사용자 계정 생성/초대            ← ADMIN
PATCH /admin/members/{id}       소속 사용자 토큰 한도(tokenLimit) 배분/조정 — 회사 전체 한도 내에서만 허용 ← ADMIN

[마스터] (B 담당)
GET   /master/signup-requests           가입 요청 리스트(상태 필터)                          ← MASTER
PATCH /master/signup-requests/{id}      요청 승인/반려(승인 시 ADMIN 계정 생성 + 회사 토큰 한도 최초 책정) ← MASTER
GET   /master/companies                 전체 회사 현황(인원수/토큰 한도/사용량)               ← MASTER
PATCH /master/companies/{id}            회사 전체 토큰 한도(tokenLimit) 조정                  ← MASTER
```

> `{id}` / 경로 파라미터로 어떤 문서·세션을 다룰지 지정한다. RAG 질의응답 엔드포인트는 SSE(Server-Sent Events)로 토큰 단위 스트리밍 응답을 반환한다.
>
> **토큰 한도 2단계 배분 구조**:
> 1. `tokenLimit(제안값) = employeeCount(회사규모) × 인당 월 토큰 한도(운영 정책값)` 로 자동 계산되어 가입 요청 시 참고용으로 표시됨
> 2. MASTER가 승인 시점에 이 제안값을 그대로 쓰거나 조정해 **`Company.tokenLimit`**(회사 전체 한도)로 확정하며, 이후에도 `PATCH /master/companies/{id}`로 재조정 가능
> 3. ADMIN은 `Company.tokenLimit` 범위 내에서 소속 `User.tokenLimit`(인당 한도)을 배분 — API에서 `sum(User.tokenLimit) ≤ Company.tokenLimit` 검증 필수
> 4. 실제 사용량(`tokenUsed`)은 `User`·`Company` 양쪽에 누적 집계해 Admin/Master 대시보드에서 잔여량을 함께 보여준다
> 

### 6.4 화면 흐름 (사용자 여정)

**회사대표(가입 요청) 여정**

```
메인화면 → "무료로 시작하기" → 가입 요청 폼 작성(회사이름/사업자번호/전화번호/이메일/인원수, 제한 토큰양 자동 계산 확인) → 제출 → 마스터 검토 대기 → (승인 시) 전화·이메일로 ADMIN 계정 안내 수신
```

**마스터 여정**

```
로그인 → 가입 요청 리스트 확인 → 요청 검토 → 승인(ADMIN 계정 자동 생성 + 회사 전체 토큰 한도 책정) 또는 반려 → 회사대표에게 전화·이메일로 별도 안내 → (이후) 필요 시 회사 토큰 한도 재조정
```

**회사 관리자(ADMIN) 여정**

```
안내받은 계정으로 로그인 → 소속 사용자(USER) 계정 생성·초대 → 회사 전체 한도 내에서 인당 토큰 한도 배분 → Admin 대시보드에서 자사 현황(문서 수, 세션 수, 토큰 사용량) 모니터링
```

**일반 사용자(USER) 여정**

```
관리자가 발급한 계정으로 로그인 → 문서 업로드(개인 문서함 또는 회사 문서함 선택, 회사 문서함은 승인 없이 즉시 업로드) → 파싱 완료 대기
  → 새 세션 시작(검색 스코프: 개인/회사 문서함 선택) → 질문 입력 → 스트리밍 답변 확인 → 인용 클릭해 원문 확인
```

**참고: 공용 컴포넌트** (A/B 공동 작업 없이도 재사용)

- 문서 카드(DocumentCard) — 문서 목록(A)과 채팅 화면 내 참조 문서 표시(B)에서 공통 사용
- 상태 뱃지(StatusBadge) — PARSING/READY/FAILED 표시에 공통 사용
- 헤더/네비게이션 — 로그인 여부·role에 따라 메뉴 분기 (공통 작업, Day 1에 함께 정의)

## 7. ERD (Phase 1 기준, 확장 필드 포함)

```
[SignupRequest]
 ├─ id (PK)
 ├─ companyName (VARCHAR)
 ├─ businessRegistrationNumber (VARCHAR, UQ)
 ├─ phone (VARCHAR)
 ├─ email (VARCHAR)
 ├─ employeeCount (INT)
 ├─ tokenLimit (INT)                          # employeeCount × 인당 토큰 한도로 자동 계산
 ├─ status (ENUM: 'PENDING', 'APPROVED', 'REJECTED')
 ├─ reviewedBy (FK -> User.id, nullable)       # 검토한 MASTER
 ├─ reviewedAt (TIMESTAMP, nullable)
 └─ createdAt

[Company]
 ├─ id (PK)
 ├─ signupRequestId (FK -> SignupRequest.id, UQ)   # 승인된 요청과 1:1 매칭
 ├─ name (VARCHAR)
 ├─ businessRegistrationNumber (VARCHAR, UQ)
 ├─ employeeCount (INT)
 ├─ tokenLimit (INT)              # 마스터가 책정한 회사 전체 토큰 한도(승인 시 자동계산값 기본, 이후 조정 가능)
 ├─ tokenUsed (INT, default 0)    # 회사 전체 누적 사용량(소속 User.tokenUsed 합계 집계)
 └─ createdAt

[User]
 ├─ id (PK)
 ├─ companyId (FK -> Company.id, nullable)     # MASTER는 소속 회사 없음(nullable)
 ├─ email (UQ)
 ├─ password
 ├─ role (ENUM: 'USER', 'ADMIN', 'MASTER')
 ├─ tokenLimit (INT, nullable)    # ADMIN이 배분한 인당 토큰 한도(회사 tokenLimit 범위 내). MASTER는 not applicable
 ├─ tokenUsed (INT, default 0)    # 개인 누적 사용량
 └─ createdAt

[Document]
 ├─ id (PK)
 ├─ ownerId (FK -> User.id)                    # 업로더
 ├─ companyId (FK -> Company.id, nullable)      # 업로더의 소속 회사(스코프 무관하게 항상 채움)
 ├─ scope (ENUM: 'PERSONAL', 'COMPANY')         # 개인 문서함 / 회사 문서함 구분
 ├─ fileName (VARCHAR)
 ├─ contentHash (VARCHAR)                       # SHA-256, UNIQUE(companyId, contentHash) WHERE scope='COMPANY' — 회사 문서함 내 완전 동일 파일 차단용. 개인 문서함은 중복 허용
 ├─ status (ENUM: 'PARSING', 'READY', 'FAILED')
 ├─ pageCount (INT)
 └─ createdAt

[Chunk]
 ├─ id (PK)
 ├─ documentId (FK -> Document.id)
 ├─ content (TEXT)
 ├─ embedding (VECTOR)
 ├─ pageNumber (INT)
 └─ rerankScore (FLOAT, nullable)   # Phase2 확장용 컬럼만 미리 확보

[ChatSession]
 ├─ id (PK)
 ├─ userId (FK -> User.id)
 ├─ scope (ENUM: 'PERSONAL', 'COMPANY')   # 세션 생성 시 선택, 이 세션의 RAG 검색 대상 결정
 ├─ title (VARCHAR)
 └─ createdAt

[ChatMessage]
 ├─ id (PK)
 ├─ sessionId (FK -> ChatSession.id)
 ├─ role (ENUM: 'user', 'assistant')
 ├─ content (TEXT)
 └─ createdAt

[Citation]
 ├─ id (PK)
 ├─ messageId (FK -> ChatMessage.id)
 ├─ chunkId (FK -> Chunk.id)
 └─ UNIQUE (messageId, chunkId)
```

> `Company`는 `SignupRequest`가 승인될 때 생성되며, 최초 `ADMIN` 계정도 이때 함께 발급된다. `ADMIN`이 이후 발급하는 `USER`는 같은 `companyId`를 갖는다. 토큰 한도는 **`Company.tokenLimit`(마스터가 책정) → `User.tokenLimit`(ADMIN이 그 범위 내에서 인당 배분)**의 2단계 구조이며, `sum(User.tokenLimit) ≤ Company.tokenLimit`을 API 레벨에서 검증한다. `Document.scope`로 개인/회사 문서함을 구분하며, 회사 문서함은 승인 절차 없이 업로드되지만 `contentHash` 중복 검사를 거친다. `ChatSession.scope`는 해당 세션의 RAG 검색이 개인/회사 문서함 중 어디를 대상으로 하는지 결정한다. `Chunk` 테이블은 두 담당자의 기능이 만나는 유일한 공유 지점입니다 (아래 9번 참고).
>

## 9. 역할 분담 — 기능(도메인) 단위 풀스택

백엔드/프론트엔드로 나누지 않고, 각자 하나의 도메인을 API부터 화면까지 처음부터 끝까지 책임집니다. "이 기능은 내가 A-Z 다 만들었다"는 스토리를 만들 수 있어 포트폴리오 설명 시 강점이 됩니다.

**공통 작업 (Day 1, 반드시 함께)**

- ERD/API 명세 확정
- 프로젝트 초기 세팅 (백엔드/프론트 보일러플레이트, DB+pgvector 연결, 배포 파이프라인 기초)
- **Auth(가입 요청 → 마스터 승인 → 계정 발급, 로그인, JWT)** — 다른 모든 기능이 이 위에서 동작하므로 반드시 먼저 끝나야 함. 둘 중 한 명이 전담하거나 짝프로그래밍으로 진행 권장

**A 담당: 문서 관리 축 (업로드부터 인덱싱까지)**

- 개인 문서함 업로드/파싱 상태 조회 — API + 화면
- 회사 문서함 업로드(콘텐츠 해시 중복 검사)/목록/삭제 — API + 화면
- 파싱·청킹·임베딩 파이프라인 (LangChain) — API
- 문서 목록/상세/삭제 — API + 화면

**B 담당: 질의응답 + 운영 축 (검색·대화·관리자 관점 전체)**

- 채팅 세션 생성/목록/히스토리 — API + 화면
- RAG 질의(벡터 검색+LLM 답변, SSE 스트리밍) — API + 화면
- PDF 뷰어 인용 하이라이팅 — 화면
- Admin 페이지 (자사 문서/세션/토큰 사용량 리스트, 소속 사용자 관리) — API + 화면
- Master 페이지 (가입 요청 승인/반려, 전체 회사 현황) — API + 화면

**접점(공유 자원)**: `Chunk` 테이블. A는 생성(파싱 시 INSERT)만, B는 조회(검색 시 SELECT)만 다루므로 겹치는 로직은 없지만, **스키마와 임베딩 차원(dimension)은 Day 1에 함께 확정**해야 합니다.

| 구분 | 담당자 | Claude Code 활용 예시 |
| --- | --- | --- |
| 문서 관리 축 | A | `문서 업로드 API와 파싱 상태 표시 화면 만들어줘` |
| 질의응답+운영 축 | B | `RAG 질의 API(SSE 스트리밍)와 채팅 화면 만들어줘` |

## 11. 확정 사항 요약 / 포트폴리오 어필 포인트

**확정 사항**

- 역할(role) 체계는 USER/ADMIN/MASTER 3단계로 단순화 — 복잡한 결재선·조직 권한 대신 `owner_id`(개인)·`companyId`(회사) 소유권 검증에 집중
- 개인 자율 회원가입 없이 **회사 단위 가입 요청 → 마스터 승인 → ADMIN 발급 → ADMIN이 사내 USER 발급**의 B2B 온보딩 구조
- 토큰 한도는 **마스터가 회사 전체 한도를 책정 → ADMIN이 그 범위 내에서 인당 한도를 배분**하는 2단계 구조(초과 배분은 API에서 검증·차단)
- 문서함은 **개인 문서함**(본인만 접근)과 **회사 문서함**(같은 회사 소속 전원 접근, 승인 절차 없이 자유 업로드, 콘텐츠 해시로 완전 중복만 자동 차단)으로 이원화, 채팅 세션은 생성 시 검색 스코프(개인/회사)를 선택
- 모든 리소스(문서·세션)는 본인 것만 접근, ADMIN도 자사 소속 리소스의 현황(리스트/사용량)만 조회하고 문서 내용 자체에는 접근하지 않음
- LLM 연동은 `LLM_PROVIDER` 스위치로 API(OpenAI/Claude)와 로컬 Ollama 간 전환 가능한 구조로 설계
- `rerankScore` 등 Phase 2 확장 필드는 Phase 1 스키마에 nullable 컬럼으로 미리 확보

**포트폴리오 어필 포인트**

1. **기능 단위 풀스택 개발 경험**: 담당 도메인(문서 관리 축 / 질의응답+운영 축)을 API 설계부터 화면 구현까지 전 과정 주도
2. **AI 협업 개발 경험**: Claude Code를 활용한 보일러플레이트/테스트 코드 생성 워크플로우
3. **확장 가능한 스키마 설계**: `rerankScore` 등 향후 Re-ranker 파인튜닝을 고려한 필드 설계
4. **보안을 고려한 LLM 연동 설계**: `LLM_PROVIDER` 스위치로 API/로컬 LLM 전환 가능한 구조 구현
5. **실무형 도메인 이해**: 업로드-파싱-검색-생성이라는 RAG 서비스 핵심 파이프라인 설계·구현
