## 1. 프로젝트 개요

**서비스명**: 멀티모달 문서 분석 & 대화형 지식베이스 플랫폼 (DocuMind AI)

**한 줄 소개**: 사용자가 업로드한 문서를 AI가 파싱·임베딩해두고, 질문하면 문서 근거(출처 페이지)와 함께 답하는 RAG 기반 대화형 지식베이스 서비스

| 항목 | 내용 |
| --- | --- |
| 팀 구성 | 2인 (기능별 풀스택 담당) + Claude Code(AI 페어 프로그래밍 도구) |
| 개발 방식 | Claude Code CLI를 활용한 보일러플레이트/테스트 코드 생성으로 개발 속도 확보 |
| 목적 | RAG 기반 AI 서비스를 A-Z 풀스택으로 구현한 AI Full-Stack Engineer 포지션 지원용 포트폴리오 확보 |

## 사용할 기술 스택

## 2. "RAG 파이프라인"이란

사용자가 올린 문서를 AI가 "먼저 찾아 읽고, 그다음 답한다"는 구조입니다. 일반 LLM이 아는 척 답하는 것과 달리, 실제 문서 내용을 근거로 답하고 출처(페이지)까지 제시합니다.

| RAG 도메인 | 일반 검색엔진 비유 |
| --- | --- |
| 문서(Document) | 색인 대상 웹페이지 |
| 청크(Chunk) | 페이지를 문단 단위로 쪼갠 색인 항목 |
| 임베딩(Embedding) | 검색어와 문단의 "의미"를 좌표로 변환한 값 |
| 검색(Retrieval) | 질문과 가장 가까운 좌표의 문단 찾기 |
| 인용(Citation) | 검색 결과에 달리는 "출처 링크" |

문서 업로드 시 처리 항목: 파일명, 소유자, 파싱 상태(status), 페이지 수, 청크 개수, 업로드 일시.

## 3. 사용자 유형 정의

> 그룹웨어의 "결재 권한"만큼 복잡하진 않지만, RAG 서비스도 **본인 문서·세션만 접근 가능**이라는 원칙이 핵심입니다.
> 

| 유형 | 정의 | 특징 |
| --- | --- | --- |
| **비로그인** | 로그인하지 않은 상태 | 메인 화면(서비스 소개)·로그인·회원가입 외 접근 불가 |
| **일반 사용자(USER)** | 로그인한 사용자 | 본인 문서 업로드/조회/삭제, 본인 채팅 세션 생성/조회, RAG 질의응답 |
| **관리자(ADMIN)** | 시스템 운영자 | USER 권한 + 전체 문서/세션/토큰 사용량 리스트 조회(Admin 대시보드) |

> **핵심 원칙**: 문서·채팅 세션 등 모든 리소스는 `owner_id` 기준으로 본인 것만 접근 가능. 역할(role) 체계는 USER/ADMIN 2단계로 단순화해 인증 로직에 시간을 쏟지 않고 RAG 파이프라인 구현에 집중한다.
>

## 4. 기능 목록 (모듈별)

> 우선순위 — **필수**: 없으면 서비스가 동작하지 않는 핵심 / **추가**: Phase 2~3 확장 계획(기획만)
> 

### 4.1 인증 / 회원

| 기능 | 접근 권한 | 우선순위 | 설명 |
| --- | --- | --- | --- |
| 회원가입 | 비로그인 | 필수 | 이메일·비밀번호 입력, 중복 확인 |
| 로그인 | 비로그인 | 필수 | JWT(Access Token) 발급 |
| 로그아웃 | USER | 필수 | 클라이언트 토큰 폐기 |
| 마이페이지 조회/수정 | 본인 | 필수 | 계정 정보 확인·수정 |

### 4.2 문서 관리 (A 담당)

| 기능 | 접근 권한 | 우선순위 | 설명 |
| --- | --- | --- | --- |
| 문서 업로드 | 본인 | 필수 | PDF 업로드 → 파싱 상태 `PARSING`으로 생성 |
| 파싱·청킹·임베딩 | 시스템(LangChain) | 필수 | 텍스트·표 추출 → 청크 분할 → 임베딩 후 pgvector 저장, 완료 시 `READY`(실패 시 `FAILED`) |
| 문서 목록/상세 조회 | 본인 | 필수 | 파일명·페이지 수·청크 수·파싱 상태 표시 |
| 문서 삭제 | 본인 | 필수 | 문서 및 연관 청크 삭제 |

### 4.3 RAG 질의응답 + 세션 관리 (B 담당)

| 기능 | 접근 권한 | 우선순위 | 설명 |
| --- | --- | --- | --- |
| 채팅 세션 생성/목록/히스토리 | 본인 | 필수 | 대화 세션 단위로 히스토리 저장·복원 |
| RAG 질의응답 | 본인 | 필수 | 질문 → 벡터 검색 → LLM 답변 생성(근거 페이지 인용) → SSE 스트리밍 |
| 인용 하이라이팅 | 본인 | 필수 | 답변의 인용 클릭 시 PDF 뷰어에서 해당 페이지·구간 하이라이트 |
| 하이브리드 검색(BM25+Dense) | 본인 | 추가(Phase 2, 기획만) | 검색 정밀도 고도화 |
| Cross-Encoder Re-ranker | 본인 | 추가(Phase 2, 기획만) | PyTorch 파인튜닝 기반 재정렬 |
| PII 마스킹 / 프롬프트 인젝션 방어 | 시스템 | 추가(Phase 2, 기획만) | 보안 강화 |

### 4.4 관리자 (Admin, B 담당)

| 기능 | 접근 권한 | 우선순위 | 설명 |
| --- | --- | --- | --- |
| 전체 문서 리스트 조회 | ADMIN | 필수 | 전 사용자 문서 현황 |
| 전체 세션 리스트 조회 | ADMIN | 필수 | 전 사용자 채팅 세션 현황 |
| 토큰 사용량 조회 | ADMIN | 필수 | LLM API 호출 토큰 사용량 집계 |

## 5. 접근 제어 규칙 (권한 매트릭스)

> **비유**: 내 서재(문서·세션)는 나만 열람·수정 가능, 관리자는 전체 서가 현황판만 볼 수 있음(타인 문서 내용에는 접근하지 않음).
> 

| 기능 | 비로그인 | USER | ADMIN |
| --- | --- | --- | --- |
| 메인 화면·로그인·회원가입 | ✅ | ✅ | ✅ |
| 본인 문서 업로드/조회/삭제 | ❌ | ✅ | ✅(본인 것만, 관리자도 타인 문서 내용엔 접근하지 않음) |
| 본인 채팅 세션/RAG 질의응답 | ❌ | ✅ | ✅(본인 것만) |
| Admin 대시보드(전체 문서/세션/사용량) | ❌ | ❌ | ✅ |

> ⚠️ **중요**: 프론트에서 버튼·메뉴를 숨기는 것만으로는 보안이 끝나지 않습니다. API 레벨(FastAPI 라우터/서비스 계층)에서 **`owner_id` 일치 여부와 role을 반드시 재검증**해야 합니다(CLAUDE.md 코딩 규칙 참고).

## 6. 화면 및 URL 설계

### 6.1 사이트맵

```
/                                        [공통] 메인화면 (비로그인 접근 가능)
│   ├─ 서비스 소개 / 히어로 섹션
│   ├─ "문서를 업로드하고 AI에게 물어보세요" 데모 미리보기
│   └─ "시작하기" CTA → /signup 연결
│
/login, /signup                         [공통]
│
├─ (로그인 시)
│   ├─ /documents                       [A] 문서 목록, 업로드
│   ├─ /documents/[id]                  [A] 문서 상세(파싱 상태·메타정보)
│   ├─ /chat                            [B] 세션 목록
│   ├─ /chat/[sessionId]                [B] Split-View 채팅 + PDF 뷰어
│   └─ /mypage                          [공통] 계정 정보
│
└─ (ADMIN 로그인 시)
    └─ /admin                           [B] 전체 문서/세션/사용량 리스트
```

### 6.2 화면별 상세

| 화면 | 경로 | 담당 | 주요 구성 요소 |
| --- | --- | --- | --- |
| 메인화면 | `/` | 공통 | 서비스 소개, 데모 미리보기, 시작하기 CTA |
| 로그인 | `/login` | 공통 | 이메일/비밀번호 입력, 로그인 버튼 |
| 회원가입 | `/signup` | 공통 | 이메일/비밀번호 입력 |
| 문서 목록 | `/documents` | A | 카드형 목록, 파싱 상태 뱃지, 업로드 버튼 |
| 문서 상세 | `/documents/[id]` | A | 파일명/페이지수/청크수, 삭제 버튼 |
| 세션 목록 | `/chat` | B | 과거 대화 세션 목록, 새 세션 시작 |
| 채팅 화면 | `/chat/[sessionId]` | B | 좌: 대화창(SSE 스트리밍), 우: PDF 뷰어(인용 하이라이팅) |
| 마이페이지 | `/mypage` | 공통 | 계정 정보 확인·수정 |
| Admin 대시보드 | `/admin` | B | 전체 문서/세션/토큰 사용량 테이블, 검색·필터 |

### 6.3 API 설계 (FastAPI 라우터 기준)

```
[인증]
POST /auth/signup            회원가입
POST /auth/login             로그인 (JWT Access Token 발급)
GET  /users/me               내 정보 조회                    ← 로그인
PATCH /users/me              내 정보 수정                    ← 로그인

[문서 관리] (A 담당)
GET    /documents            내 문서 목록 조회               ← 로그인
POST   /documents            문서 업로드(파싱·청킹·임베딩 파이프라인 트리거) ← 로그인
GET    /documents/{id}       문서 상세(파싱 상태·페이지수·청크수) 조회 ← 소유자
DELETE /documents/{id}       문서 삭제(연관 청크 포함)        ← 소유자

[채팅 / RAG 질의응답] (B 담당)
GET  /chat/sessions                  내 세션 목록 조회         ← 로그인
POST /chat/sessions                  세션 생성                ← 로그인
GET  /chat/sessions/{id}/messages    세션 히스토리 조회        ← 소유자
POST /chat/sessions/{id}/messages    질문 전송 → 벡터 검색 → LLM 답변(SSE 스트리밍, 인용 포함) ← 소유자

[관리자] (B 담당)
GET /admin/documents         전체 문서 리스트                 ← ADMIN
GET /admin/sessions          전체 세션 리스트                 ← ADMIN
GET /admin/usage             토큰 사용량 집계                 ← ADMIN
```

> `{id}` / 경로 파라미터로 어떤 문서·세션을 다룰지 지정한다. RAG 질의응답 엔드포인트는 SSE(Server-Sent Events)로 토큰 단위 스트리밍 응답을 반환한다.
> 

### 6.4 화면 흐름 (사용자 여정)

**일반 사용자 여정**

```
메인화면 → 회원가입 → 로그인 → 문서 업로드 → 파싱 완료 대기 → 새 세션 시작 → 질문 입력 → 스트리밍 답변 확인 → 인용 클릭해 원문 확인
```

**관리자 여정**

```
로그인 → Admin 대시보드에서 전체 현황(문서 수, 세션 수, 토큰 사용량) 모니터링
```

**참고: 공용 컴포넌트** (A/B 공동 작업 없이도 재사용)

- 문서 카드(DocumentCard) — 문서 목록(A)과 채팅 화면 내 참조 문서 표시(B)에서 공통 사용
- 상태 뱃지(StatusBadge) — PARSING/READY/FAILED 표시에 공통 사용
- 헤더/네비게이션 — 로그인 여부·role에 따라 메뉴 분기 (공통 작업, Day 1에 함께 정의)

## 7. ERD (Phase 1 기준, 확장 필드 포함)

```
[User]
 ├─ id (PK)
 ├─ email (UQ)
 ├─ password
 ├─ role (ENUM: 'USER', 'ADMIN')
 └─ createdAt

[Document]
 ├─ id (PK)
 ├─ ownerId (FK -> User.id)
 ├─ fileName (VARCHAR)
 ├─ status (ENUM: 'PARSING', 'READY', 'FAILED')
 ├─ pageCount (INT)
 └─ createdAt

[Chunk]
 ├─ id (PK)
 ├─ documentId (FK -> Document.id)
 ├─ content (TEXT)
 ├─ embedding (VECTOR)
 ├─ pageNumber (INT)
 └─ rerankScore (FLOAT, nullable)   # Phase2 확장용 컬럼만 미리 확보

[ChatSession]
 ├─ id (PK)
 ├─ userId (FK -> User.id)
 ├─ title (VARCHAR)
 └─ createdAt

[ChatMessage]
 ├─ id (PK)
 ├─ sessionId (FK -> ChatSession.id)
 ├─ role (ENUM: 'user', 'assistant')
 ├─ content (TEXT)
 └─ createdAt

[Citation]
 ├─ id (PK)
 ├─ messageId (FK -> ChatMessage.id)
 ├─ chunkId (FK -> Chunk.id)
 └─ UNIQUE (messageId, chunkId)
```

> `Chunk` 테이블은 두 담당자의 기능이 만나는 유일한 공유 지점입니다 (아래 9번 참고).

## 8. 개발 전략: Claude Code 활용

1. **CLAUDE.md 규칙 파일** — 프로젝트 루트에 배치해 Claude Code가 코딩 컨벤션/ERD/타입 정의를 항상 인지하도록 세팅
2. **보일러플레이트 자동 생성** — FastAPI 라우터, Next.js 페이지 골격을 Claude Code로 생성 후 비즈니스 로직(RAG 파이프라인 등)만 직접 채움
3. **스키마 ↔ 프론트 타입 동기화** — 백엔드 Pydantic 스키마 변경 시 Claude Code로 프론트 TypeScript 인터페이스 갱신 요청

**CLAUDE.md 예시**

```markdown
# Project Guide for Claude Code

## Tech Stack
- Backend: FastAPI, SQLAlchemy, PostgreSQL + pgvector
- Frontend: Next.js, TypeScript, Tailwind CSS
- AI: LangChain, OpenAI/Claude API (LLM_PROVIDER 스위치로 로컬 Ollama 전환 가능)

## Coding Rules
- 계층 단위(Router-Service-Repository)로 구조화
- 요청/응답 스키마에 Pydantic 모델 필수
- 문서/세션 접근 시 owner_id 검증 필수 (본인 리소스만 접근)
- Conventional Commits(feat:, fix:, docs:, refactor:) 사용
```

## 9. 역할 분담 — 기능(도메인) 단위 풀스택

백엔드/프론트엔드로 나누지 않고, 각자 하나의 도메인을 API부터 화면까지 처음부터 끝까지 책임집니다. "이 기능은 내가 A-Z 다 만들었다"는 스토리를 만들 수 있어 포트폴리오 설명 시 강점이 됩니다.

**공통 작업 (Day 1, 반드시 함께)**

- ERD/API 명세 확정
- 프로젝트 초기 세팅 (백엔드/프론트 보일러플레이트, DB+pgvector 연결, 배포 파이프라인 기초)
- **Auth(회원가입/로그인/JWT)** — 다른 모든 기능이 이 위에서 동작하므로 반드시 먼저 끝나야 함. 둘 중 한 명이 전담하거나 짝프로그래밍으로 진행 권장

**A 담당: 문서 관리 축 (업로드부터 인덱싱까지)**

- 문서 업로드/파싱 상태 조회 — API + 화면
- 파싱·청킹·임베딩 파이프라인 (LangChain) — API
- 문서 목록/상세/삭제 — API + 화면

**B 담당: 질의응답 + 운영 축 (검색·대화·관리자 관점 전체)**

- 채팅 세션 생성/목록/히스토리 — API + 화면
- RAG 질의(벡터 검색+LLM 답변, SSE 스트리밍) — API + 화면
- PDF 뷰어 인용 하이라이팅 — 화면
- Admin 페이지 (전체 문서/세션/토큰 사용량 리스트) — API + 화면

**접점(공유 자원)**: `Chunk` 테이블. A는 생성(파싱 시 INSERT)만, B는 조회(검색 시 SELECT)만 다루므로 겹치는 로직은 없지만, **스키마와 임베딩 차원(dimension)은 Day 1에 함께 확정**해야 합니다.

| 구분 | 담당자 | Claude Code 활용 예시 |
| --- | --- | --- |
| 문서 관리 축 | A | `문서 업로드 API와 파싱 상태 표시 화면 만들어줘` |
| 질의응답+운영 축 | B | `RAG 질의 API(SSE 스트리밍)와 채팅 화면 만들어줘` |

## 11. 확정 사항 요약 / 포트폴리오 어필 포인트

**확정 사항**

- 역할(role) 체계는 USER/ADMIN 2단계로 단순화 — 복잡한 결재선·조직 권한 대신 `owner_id` 소유권 검증에 집중
- 모든 리소스(문서·세션)는 본인 것만 접근, 관리자도 타인 문서 내용에는 접근하지 않고 현황(리스트/사용량)만 조회
- LLM 연동은 `LLM_PROVIDER` 스위치로 API(OpenAI/Claude)와 로컬 Ollama 간 전환 가능한 구조로 설계
- `rerankScore` 등 Phase 2 확장 필드는 Phase 1 스키마에 nullable 컬럼으로 미리 확보

**포트폴리오 어필 포인트**

1. **기능 단위 풀스택 개발 경험**: 담당 도메인(문서 관리 축 / 질의응답+운영 축)을 API 설계부터 화면 구현까지 전 과정 주도
2. **AI 협업 개발 경험**: Claude Code를 활용한 보일러플레이트/테스트 코드 생성 워크플로우
3. **확장 가능한 스키마 설계**: `rerankScore` 등 향후 Re-ranker 파인튜닝을 고려한 필드 설계
4. **보안을 고려한 LLM 연동 설계**: `LLM_PROVIDER` 스위치로 API/로컬 LLM 전환 가능한 구조 구현
5. **실무형 도메인 이해**: 업로드-파싱-검색-생성이라는 RAG 서비스 핵심 파이프라인 설계·구현
